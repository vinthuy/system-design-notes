# 第26章：支付系统

## 引言
本章我们将设计一个**支付系统**，它支撑着所有现代**电子商务**。

**支付系统**用于结算金融交易，转移货币价值。

---

## 步骤 1：理解问题并确定设计范围
 * C：我们要构建的是哪种类型的支付系统？
 * I：一个面向电子商务系统的支付后端，类似于 Amazon.com。它处理所有与资金流转相关的事务。
 * C：支持哪些支付选项——信用卡、PayPal、银行卡等？
 * I：系统在现实中应当支持所有这些选项。就本次面试而言，我们可以使用信用卡支付。
 * C：我们自己处理信用卡交易吗？
 * I：不，我们使用第三方提供商，例如 Stripe、Braintree、Square 等。
 * C：我们会在系统中存储信用卡数据吗？
 * I：出于合规原因，我们不会在自己的系统中直接存储信用卡数据。我们依赖第三方支付处理商。
 * C：这个应用是全球性的吗？我们需要支持不同的货币和国际支付吗？
 * I：应用是全球性的，但就本次面试而言，我们假设只使用一种货币。
 * C：我们每天支持多少笔支付交易？
 * I：每天100万笔交易。
 * C：我们需要支持付款流程吗，例如每月向收款方付款？
 * I：是的，我们需要支持这一点。
 * C：还有其他我需要注意的事项吗？
 * I：我们需要支持对账，以修复与内部和外部系统通信时出现的任何不一致。

### **功能需求**
 * 收款流程——支付系统代表商家从客户处收取资金
 * 付款流程——支付系统向世界各地的卖家付款

### **非功能需求**
 * 可靠性与容错性。失败的支付需要被谨慎处理
 * 需要在内部系统与外部系统之间建立对账机制。

### **粗略估算**
该系统每天需要处理100万笔交易，也就是每秒10笔交易。

这对任何数据库系统而言都不是高吞吐量，因此它不是本次面试的重点。

### **收款流程**
以下是收款流程的高层次概览：

<div style="margin-left:3rem">
    <img src="./images/payin-flow-high-level.png" alt="pay-in-flow-high-level" width="500" />
</div>

 * 支付服务——接受支付事件并协调支付流程。它通常还会使用第三方提供商进行风险检查，以识别反洗钱（AML）违规或犯罪活动。
 * 支付执行器——通过支付服务提供商（PSP）执行单笔支付订单。一个支付事件可能包含多个支付订单。
 * 支付服务提供商（PSP）——将资金从一个账户转移到另一个账户，例如从买家的信用卡账户转移到电子商务网站的银行账户。
 * 卡组织——处理信用卡操作的组织，例如 Visa、MasterCard 等。
 * 账本——保存所有支付交易的财务记录。
 * 钱包——保存所有商家的账户余额。

以下是一个收款流程的示例：
 * 用户点击“下单”，一个支付事件被发送到支付服务
 * 支付服务将该事件存储到其数据库中
 * 支付服务针对该支付事件中的所有支付订单调用支付执行器
 * 支付执行器将支付订单存储到其数据库中
 * 支付执行器调用外部 PSP 处理信用卡支付
 * 支付执行器处理完支付后，支付服务更新钱包，以记录卖家拥有多少资金
 * 钱包服务将更新后的余额信息存储到其数据库中
 * 支付服务调用账本记录所有资金流转

### **支付服务的 API**
```
POST /v1/payments
{
  "buyer_info": {...},
  "checkout_id": "some_id",
  "credit_card_info": {...},
  "payment_orders": [{...}, {...}, {...}]
}
```

示例`payment_order`：
```
{
  "seller_account": "SELLER_IBAN",
  "amount": "3.15",
  "currency": "USD",
  "payment_order_id": "globally_unique_payment_id"
}
```

注意事项：
 * `payment_order_id`会被转发给 PSP 以对支付去重，也就是说，它就是幂等键。
 * amount 字段是`string`类型，因为`double`不适合表示货币金额。

```
GET /v1/payments/{:id}
```

该端点根据`payment_order_id`返回单笔支付的执行状态。

### **支付服务的数据模型**
我们需要维护两张表——`payment_events`和`payment_orders`。

对于支付而言，性能通常不是重要因素，但强一致性是。

选择数据库时的其他考虑因素：
 * 有足够多的 DBA 人才可供招聘，以管理数据库
 * 有可靠的过往记录，证明该数据库已被其他大型金融机构使用
 * 支持工具的丰富程度
 * 选择传统 SQL 而非 NoSQL/NewSQL，以获得其 ACID 保证

`payment_events`表包含以下内容：
 * `checkout_id`——字符串，主键
 * `buyer_info`——字符串（个人备注——可能指向另一张表的外键更合适）
 * `seller_info`——字符串（个人备注——同上）
 * `credit_card_info`——取决于卡提供商
 * `is_payment_done`——布尔值

`payment_orders`表包含以下内容：
 * `payment_order_id`——字符串，主键
 * `buyer_account`——字符串
 * `amount`——字符串
 * `currency`——字符串
 * `checkout_id`——字符串，外键
 * `payment_order_status`——枚举（`NOT_STARTED`、`EXECUTING`、`SUCCESS`、`FAILED`）
 * `ledger_updated`——布尔值
 * `wallet_updated`——布尔值

注意事项：
 * 一个支付事件会关联多个支付订单
 * 收款流程不需要`seller_info`，它只在付款流程中需要
 * `ledger_updated`和`wallet_updated`在调用相应服务记录支付结果时被更新
 * 支付状态流转由后台任务管理，该任务检查进行中支付的更新，并在支付未在合理时间范围内处理时触发告警

### **复式记账账本系统**
复式记账机制是任何支付系统的关键。它是一种跟踪资金流转的机制，始终对两个账户应用资金操作，其中一个账户的余额增加（贷记），另一个账户的余额减少（借记）：

| 账户 | 借方 | 贷方 |
|---------|-------|--------|
| 买家   | $1    |        |
| 卖家  |       | $1     |

所有交易分录之和始终为零。该机制为系统中的所有资金流转提供了端到端的可追溯性。

## 步骤 3：设计深入探讨
本节聚焦于让系统更快、更健壮、更安全。

### **PSP 集成**
如果我们的系统能够直接连接银行或卡组织，那么无需 PSP 即可完成支付。
这类连接非常罕见且不常见，通常由有能力证明该投资合理性的大公司完成。

如果我们走传统路线，PSP 可以通过以下两种方式之一进行集成：
 * 通过 API 集成，前提是我们的支付系统能够采集支付信息
 * 通过托管支付页面集成，以避免处理支付信息相关的法规

托管支付页面的工作流程如下：

<div style="margin-left:3rem">
    <img src="./images/hosted-payment-page-workflow.png" alt="hosted-payment-page-workflow" width="500" />
</div>

 * 用户在浏览器中点击“结账”按钮
 * 客户端携带支付订单信息调用支付服务
 * 收到支付订单信息后，支付服务向 PSP 发送支付注册请求。
 * PSP 接收币种、金额、有效期等支付信息，以及一个用于幂等目的的 UUID，通常是支付订单的 UUID。
 * PSP 返回一个令牌，该令牌唯一标识此次支付注册。该令牌被存储在支付服务的数据库中。
 * 令牌存储完成后，用户会看到 PSP 托管的支付页面。该页面使用令牌以及用于成功/失败的重定向 URL 进行初始化。
 * 用户在 PSP 页面上填写支付详情，PSP 处理支付并返回支付状态
 * 用户随后被重定向回 redirectURL。重定向 URL 示例——`https://your-company.com/?tokenID=JIOUIQ123NSF&payResult=X324FSa`
 * 在异步路径上，PSP 通过 webhook 调用我们的支付服务，将支付结果告知我们的后端
 * 支付服务根据收到的 webhook 记录支付结果

### **对账**
上一节讲解了支付的正常路径。异常路径通过后台对账流程来检测并处理。

每晚，PSP 会发送一个结算文件，我们的系统用它来将外部系统的状态与内部系统的状态进行比对。

<div style="margin-left:3rem">
    <img src="./images/settlement-report.png" alt="settlement-report" width="500" />
</div>

该流程也可用于检测内部不一致，例如账本与钱包服务之间的不一致。

不一致由财务团队人工处理。不一致的处理方式如下：
 * 可分类，因此是已知的不一致，可以通过标准流程进行调整
 * 可分类，但无法自动处理。由财务团队人工调整
 * 不可分类。由财务团队人工调查并调整

### **处理支付处理延迟**
在某些情况下，一笔支付可能需要数小时才能完成，尽管通常只需几秒钟。

这可能由以下原因导致：
 * 支付被标记为高风险，需要有人工审核
 * 信用卡需要额外保护，例如 3D Secure 认证，这需要持卡人提供额外信息才能完成

这些情况通过以下方式处理：
 * 等待 PSP 在支付完成时向我们发送 webhook，或者在 PSP 不提供 webhook 时轮询其 API
 * 向用户显示“处理中”状态，并给他们一个可以查看支付更新的页面。我们还可以在支付完成后给他们发送一封电子邮件

### **内部服务之间的通信**
服务之间相互通信时使用两种类型的通信模式——同步和异步。

同步通信（即 HTTP）在小规模系统中运行良好，但随着规模扩大而表现不佳：
 * 性能低——随着调用链中涉及的服务增多，请求-响应周期变长
 * 故障隔离差——如果 PSP 或任何其他服务失败，用户将收不到响应
 * 紧耦合——发送方需要知道接收方
 * 难以扩展——由于没有缓冲区，难以支撑突发的流量增长

异步通信可以分为两类。

单个接收者——多个接收者订阅同一个主题，但消息只被处理一次：

<div style="margin-left:3rem">
    <img src="./images/single-receiver.png" alt="single-receiver" width="500" />
</div>

多个接收者——多个接收者订阅同一个主题，但消息会被转发给所有接收者：

<div style="margin-left:3rem">
    <img src="./images/multiple-receiver.png" alt="multiple-receiver" width="500" />
</div>

后一种模型很适合我们的支付系统，因为一笔支付可以触发多个副作用，由不同的服务处理。

简而言之，同步通信更简单，但不允许服务自治。
异步通信以简单性和一致性换取可扩展性和韧性。

### **处理失败的支付**
每个支付系统都需要处理失败的支付。以下是我们将用于实现这一点的一些机制：
 * 跟踪支付状态——每当支付失败时，我们可以根据支付状态决定是重试还是退款。
 * 重试队列——我们将要重试的支付发布到重试队列
 * 死信队列——已终态失败的支付被推送到死信队列，在那里可以对失败的支付进行调试和检查。

### **恰好一次投递**
我们需要确保一笔支付恰好被处理一次，以避免向客户重复扣款。

一个操作如果同时满足至少一次和至多一次，那么它就是恰好一次执行。

为了实现至少一次的保证，我们将使用重试机制：

<div style="margin-left:3rem">
    <img src="./images/retry-mechanism.png" alt="retry-mechanism" width="500" />
</div>

以下是一些决定重试间隔的常见策略：
 * 立即重试——客户端在失败后立即发送另一个请求
 * 固定间隔——在重试支付前等待固定的时长
 * 递增间隔——在每次重试之间逐步增加重试间隔
 * 指数退避——在后续重试之间将重试间隔翻倍
 * 取消——客户端取消请求。当错误是终态错误或达到重试阈值时会发生这种情况

根据经验，默认采用指数退避重试策略。一个好的做法是让服务端使用`Retry-After`响应头指定重试间隔。

重试的一个问题是服务端可能会处理同一笔支付两次：
 * 客户端点击了两次“支付”按钮，因此被扣款两次
 * 支付已被 PSP 成功处理，但未被下游服务（账本、钱包）处理。重试导致支付再次被 PSP 处理

为了解决重复支付问题，我们需要使用幂等机制——即一个操作被应用多次也只被处理一次的特性。

从 API 的角度看，客户端可以进行多次调用，而产生相同的结果。
幂等性由请求中的一个特殊头部（例如`idempotency-key`）管理，该头部通常是一个 UUID。

<div style="margin-left:3rem">
    <img src="./images/idempotency-example.png" alt="idempotency-example" width="500" />
</div>

幂等性可以通过数据库添加唯一键约束的机制来实现：
 * 服务端尝试在数据库中插入新行
 * 由于唯一键约束冲突，插入失败
 * 服务端检测到该错误，转而将已存在的对象返回给客户端

幂等性也应用在 PSP 一侧，使用前面讨论过的 nonce。PSP 会注意不重复处理具有相同 nonce 的支付。

### **一致性**
在一笔支付的生命周期中会调用多个有状态服务——PSP、账本、钱包、支付服务。

任意两个服务之间的通信都可能失败。
我们可以通过实现恰好一次处理和对账，来确保所有服务之间数据的最终一致性。

如果使用复制，我们就必须处理复制延迟，这可能导致用户在主库与从库之间观察到不一致的数据。

为了缓解这一点，我们可以让所有读和写都由主库处理，而仅将副本用于冗余和故障转移。
或者，我们可以通过使用 Paxos 或 Raft 等共识算法来确保副本始终保持同步。
我们也可以使用基于共识的分布式数据库，例如 YugabyteDB 或 CockroachDB。

### **支付安全**
以下是一些可用于确保支付安全的机制：
 * 请求/响应窃听——我们可以使用 HTTPS 来保护所有通信
 * 数据篡改——强制执行加密和完整性监控
 * 中间人攻击——使用 SSL 与证书固定
 * 数据丢失——跨多个区域复制数据并创建数据快照
 * DDoS 攻击——实施限流和防火墙
 * 卡盗用——使用令牌，而不是在我们的系统中存储真实的卡片信息
 * PCI 合规——针对处理品牌信用卡的组织的一项安全标准
 * 欺诈——地址验证、卡验证值（CVV）、用户行为分析等
