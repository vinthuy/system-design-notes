# 第 10 章：设计通知系统

## 引言
**通知系统**对现代应用至关重要，它能提供及时的更新，例如商品通知、事件、优惠和告警。通知可以通过以下方式发送：
1. **推送通知**（移动端或桌面端），
2. **短信**，以及
3. **电子邮件**。

本章聚焦于设计一个可扩展的系统，使其能够每天发送数百万条通知。

---

## 第 1 步：理解问题
### 需求
- **通知类型：** 推送通知、短信和电子邮件。
- **投递：** 软实时系统，延迟尽可能小。
- **平台：** iOS、Android 和桌面端。
- **触发方式：** 通知可以由客户端应用触发，也可以在服务端定时调度。
- **规模：**
  - **推送通知：** 每天 1000 万条，
  - **短信：** 每天 100 万条，
  - **电子邮件：** 每天 500 万条。
- **退订支持：** 用户可以关闭特定类型的通知。

---

## 第 2 步：高层设计

### 组件

1. **通知类型：**
   - **iOS 推送通知：** 使用 **Apple Push Notification Service（APNS）**。
   - **Android 推送通知：** 使用 **Firebase Cloud Messaging（FCM）**。
   - **短信：** 使用 Twilio 或 Nexmo 等第三方服务。
   - **电子邮件：** 使用 SendGrid 或 Mailchimp 等商业电子邮件服务。

2. **收集联系信息：**
   <div style="margin-left:3rem">
      <img src="./images/contact-info-gathering.png" alt="收集联系信息" width="500">
   </div>

   - 在应用安装或注册时收集设备令牌、电话号码或电子邮件地址。
   - 将联系信息存储在数据库中：
     - **设备令牌表：** 用于推送通知。
     - **用户表：** 用于电子邮件和电话号码。


3. **通知发送流程：**

   <div style="margin-left:3rem">
      <img src="./images/high-level-design.png" alt="高层设计" width="500">
   </div>

   - **触发服务：**
      - 生成事件以发起通知（例如账单提醒、物流更新）。
      - 该服务可以是一个微服务、一个定时任务（cron job），或一个触发通知发送事件的分布式系统。
   - **通知服务器：** 
      - 提供服务 API，供各服务发送通知。 
      - 执行基本校验，以验证电子邮件、电话号码。
      - 查询数据库或缓存，以获取渲染通知所需的数据。
   - **第三方服务：** 向用户投递通知。

     

### 初始设计中的挑战
- **单点故障（SPOF）：** 一台通知服务器崩溃就可能导致整个系统不可用。
- **可扩展性问题：** 数据库、缓存和处理组件难以独立扩展。
- **性能瓶颈：** 发送通知对资源需求很高。

### 改进后的设计

   <div style="margin-left:3rem">
      <img src="./images/improved-design.png" alt="改进后的设计" width="500">
   </div>

- 将数据库和缓存移出通知服务器。
- 引入**水平扩展**，使用多台通知服务器。
- 使用**消息队列**解耦系统组件。
   - 当需要发送大量通知时，消息队列充当缓冲区。
- 增加 worker，从消息队列中拉取通知事件，并发送到相应的第三方服务。

   

---

## 第 3 步：深入设计

### 可靠性
1. **防止数据丢失：** 
   <div style="margin-left:3rem">
   <img src="./images/data-loss.png" alt="数据丢失" width="400">
   </div>

   - 将通知数据持久化到数据库，并实现重试机制。 
   - 引入通知日志数据库以实现数据持久化。


2. **去重：** 
   - 检查事件 ID，避免发送重复通知。
   - 当通知事件首次到达时，通过检查事件 ID 判断此前是否见过该事件。
如果见过则丢弃，否则就发送该通知。 


### 其他组件
   <div style="margin-left:3rem">
   <img src="./images/events-tracking.png" alt="事件追踪" width="400">
   </div>

1. **通知模板：** 预格式化的模板，用于保证通知的一致性与高效性。
2. **通知设置：**
   - 用户可以针对特定渠道（推送、短信或电子邮件）选择接收或退订。
   - 存储在专门的通知设置表中。
3. **限流：** 限制向用户发送通知的频率。
4. **重试机制：** 当第三方服务失败时重试发送通知。
5. **监控队列：** 跟踪排队中的通知，以动态扩展 worker。
6. **事件追踪：** 收集打开率、点击率和参与度等指标。


### 安全性
- 使用 **AppKey** 和 **AppSecret** 对推送通知的 API 进行认证与保护。

### 通知流程

   <div style="margin-left:3rem">
   <img src="./images/updated-design.png" alt="更新后的设计" width="500">
   </div>

1. 触发服务调用 API 发送通知。
2. 通知服务器校验请求，并从缓存或数据库获取元数据。
3. 通知事件被发送到消息队列。
4. worker 处理事件并与第三方服务交互。
5. 第三方服务向用户投递通知。


---

## 关键优化
1. **水平扩展：** 增加更多通知服务器以分散负载。
2. **消息队列：** 解耦处理过程以应对高流量。
3. **缓存：** 通过缓存频繁访问的数据来降低延迟。
4. **分布式爬取：** 按地理位置优化消息投递，以获得更好的性能。
