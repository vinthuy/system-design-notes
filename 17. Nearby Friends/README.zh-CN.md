# 第 17 章：附近的朋友

## 引言

本章聚焦于为一个应用设计可扩展的后端，该应用让用户能够共享自己的位置，并发现**附近**的朋友。

与邻近那一章的主要区别在于，在这个问题中，**位置会不断变化**，而在那一章中，商家地址基本保持不变。

---

## 第1步：理解问题并确立设计范围

用于推动面试的一些问题：
 * C: 地理上多近才被视为“附近”？
 * I: 5英里，这个数字应当可配置
 * C: 距离是按直线距离计算，还是考虑诸如朋友之间隔着一条河的情况
 * I: 是的，这是一个合理的假设
 * C: 这个应用有多少用户？
 * I: 10亿用户，其中10%使用附近的朋友功能
 * C: 我们需要存储位置历史吗？
 * I: 需要，例如它对机器学习有价值
 * C: 我们能否假定不活跃的朋友会在10分钟后从该功能中消失
 * I: 是的
 * C: 我们需要考虑GDPR等法规吗？
 * I: 不需要，为了简单起见

### **功能需求**

 * 用户应当能够在移动应用中看到附近的朋友。每个朋友都带有距离和时间戳，用于表明位置是何时更新的
 * 附近的朋友列表应当每隔几秒更新一次

### **非功能需求**

- **低延迟**：接收位置更新时不能有太大延迟，这一点很重要
- **可靠性**：偶发丢失数据点是可以接受的，但系统整体上应当可用
- **最终一致性**：位置数据存储不需要强一致性。不同副本在接收位置数据时延迟几秒是可接受的

### **粗略估算**

用于确定潜在规模的一些估算：
 * 附近的朋友是指5英里半径内的朋友
 * 位置刷新间隔为30秒。人的步行速度很慢，因此无需过于频繁地更新位置。
 * 平均每天有1亿用户使用该功能，\w 10%为并发用户，即1000万
 * 平均而言，一个用户有400个朋友，他们全都使用附近的朋友功能
 * 应用每页显示20个附近的朋友
 * **位置更新QPS** = 1000万 / 30 == ~334k次更新每秒

## 第2步：提出高层设计并获得认可

在探讨API与数据模型设计之前，我们先研究将要使用的通信协议，因为它不像传统的请求-响应通信模型那样普遍。

### **高层设计**

在高层上，我们希望在对等端之间建立高效的消息传递。这可以通过点对点协议实现，但对于连接不稳定、功耗约束严格的移动应用来说，这并不实际。

更实际的做法是使用一个共享后端，作为向你想触达的好友进行扇出的机制：

<div style="margin-left:3rem">
    <img src="./images/fan-out-backend.png" alt="fan-out-backend" width="500" />
</div>

后端做什么？
 * 接收来自所有活跃用户的位置更新
 * 对每次位置更新，找出所有应当收到该更新的活跃用户，并将其转发给他们
 * 如果朋友之间的距离超过配置的阈值，则不转发位置数据

这听起来简单，但挑战在于为我们所处的规模设计系统。

我们先从一个更简单的设计开始，并在深度探讨中讨论更高级的方案：

<div style="margin-left:3rem">
    <img src="./images/simple-high-level-design.png" alt="simple-high-level-design" width="500" />
</div>

- **负载均衡器**：将流量分发到rest API服务器以及双向web socket服务器
- **Rest API服务器**：处理辅助任务，例如管理好友、更新资料等
- **Websocket服务器**：有状态服务器，将位置更新请求转发给相应的客户端。它还负责在初始化时向移动客户端预置附近朋友的位置（稍后详细讨论）。
- **Redis位置缓存**：用于存储每个活跃用户的最新位置数据。缓存中的每个条目都设置了TTL。当TTL过期时，用户不再活跃，其数据会从缓存中移除。
- **用户数据库**：存储用户与好友关系数据。可以使用关系型数据库或NoSQL数据库。
- **位置历史数据库**：存储用户位置数据的历史记录，不一定直接用于附近的朋友功能，而是用于跟踪历史数据以进行分析
- **Redis pubsub**：用作轻量级消息总线，它为每个用户频道提供不同的主题以承载位置更新。

</div>

在上面的示例中，WebSocket服务器订阅连接到它们的用户所对应的频道，并在收到位置更新时将其转发给相应的用户。

### **周期性位置更新**

以下是周期性位置更新的工作流程：

<div style="margin-left:3rem">
    <img src="./images/periodic-location-update.png" alt="periodic-location-update" width="500" />
</div>

 * 移动客户端向负载均衡器发送位置更新
 * 负载均衡器将位置更新转发到该客户端对应的WebSocket服务器的持久连接上
 * WebSocket服务器将位置数据保存到位置历史数据库
 * 位置数据在位置缓存中更新。WebSocket服务器还会在内存中保存位置数据，以便后续为该用户计算距离
 * WebSocket服务器通过redis pub sub在用户的频道中发布位置数据
 * Redis pubsub将该位置更新广播给该用户频道的所有订阅者，即负责该用户好友的那些服务器
 * 订阅的web socket服务器收到位置更新，计算该更新应发送给哪些用户，并发送出去

平均而言，需要转发40次位置更新，因为一个用户平均有400个好友，其中10%同时在线。

### **API设计**

我们需要支持的WebSocket例程：
 * 周期性位置更新 - 用户向WebSocket服务器发送位置数据
 * 客户端接收位置更新 - 服务器发送好友位置数据和时间戳
 * WebSocket客户端初始化 - 客户端发送用户位置，服务器返回附近好友的位置数据
 * 订阅新好友 - WebSocket服务器发送一个好友ID，移动客户端应当跟踪该好友，例如当好友首次上线时
 * 取消订阅好友 - WebSocket服务器发送一个好友ID，移动客户端应当取消对该好友的订阅，例如因为好友下线了

HTTP API - 用于辅助职责的传统请求/响应负载。

### **数据模型**

 * 位置缓存将存储`user_id`与`lat,long,timestamp`之间的映射。Redis是这个缓存的好选择，因为我们只关心当前位置，而且它支持TTL淘汰，这正是我们所需的。
 * 位置历史表存储相同的数据，但存在一张关系型表中，\w上述四列。Cassandra可以用于这份数据，因为它针对写密集负载做了优化。

## 第3步：设计深度探讨

让我们讨论如何扩展高层设计，使其能够在我们目标规模下工作。

### **每个组件的扩展性如何？**

- **API服务器**：可以通过自动伸缩组和复制服务器实例轻松扩展
- **WebSocket服务器**：我们可以轻松地横向扩展ws服务器，但在拆除服务器时需要确保优雅地关闭现有连接。例如，我们可以在负载均衡器中把服务器标记为“draining”，并在它最终从服务器池中移除之前停止向它发送连接
- **客户端初始化**：当客户端首次连接到服务器时，它获取用户的好友，在redis pubsub上订阅他们的频道，从缓存中获取他们的位置，最后转发给客户端
- **用户数据库**：我们可以基于user_id对数据库进行分片。通过一个由专门团队管理的专用服务和API来暴露用户/好友数据，也可能是合理的
- **位置缓存**：我们可以通过启动多个redis节点来轻松地分片缓存。此外，TTL限制了我们某一时刻可能占用的最大内存。但我们仍需处理大量的写负载
- **Redis pub/sub服务器**：我们利用了这样一个事实：如果频道已初始化但未被使用，则不会消耗内存。因此，我们可以为所有使用附近的朋友功能的用户预先分配频道，以避免诸如在用户上线时启动新频道并通知活跃WebSocket服务器之类的麻烦

### **深入探讨redis pub/sub组件的扩展**

我们将需要大约200GB内存来维护所有pub/sub频道。这可以通过使用2台各100GB的redis服务器来实现。

鉴于我们每秒需要推送约1400万次位置更新，假设单台服务器每秒能处理约10万次推送，我们则需要至少140台redis服务器来处理这一负载。

因此，我们需要一个分布式redis服务器集群来处理如此密集的CPU负载。

为了支持分布式redis集群，我们需要利用服务发现组件，例如zookeeper或etcd，来跟踪哪些服务器还活着。

我们需要在服务发现组件中编码的数据如下：

<div style="margin-left:3rem">
    <img src="./images/channel-distribution-data.png" alt="channel-distribution-data" width="500" />
</div>

WebSocket服务器使用从zookeeper获取的这些编码数据来确定某个特定频道位于哪里。为了提高效率，哈希环数据可以缓存在每个WebSocket服务器的内存中。

关于服务器集群的扩容或缩容，我们可以设置一个每日任务，根据历史流量数据按需扩展集群。我们还可以超额配置集群以应对负载峰值。

redis集群可以被视为有状态存储服务器，因为要为频道维护一些状态，并且需要与订阅者协调，以便它们将订阅移交给集群中新配置的节点。

在扩展操作期间，我们必须注意一些潜在问题：
 * 由于频道被四处迁移，web socket服务器会发出大量重新订阅请求
 * 操作期间客户端可能会错过一些位置更新，这在本问题中是可接受的，但我们仍应尽量减少这种情况的发生。考虑在当天流量最低时执行此类操作。
 * 我们可以利用一致性哈希来尽量减少在增加/删除服务器时迁移的频道数量

### **添加/移除好友**

每当添加/移除好友时，负责受影响用户的WebSocket服务器需要订阅/取消订阅该好友的频道。

由于“附近的朋友”功能是更大应用的一部分，我们可以假定：只要发生上述任一事件，移动客户端侧就可以注册一个回调，由客户端向WebSocket服务器发送消息以执行相应操作。

### **好友数量很多的用户**

我们可以对一个人能拥有的好友总数设置上限，例如facebook最多有5000个好友的上限。

处理“鲸鱼”用户的WebSocket服务器自身可能负载更高，但只要有足够的web socket服务器，就应该没问题。

### **Redis pub/sub的替代方案**

使用Redis做pub/sub的一种替代方案是利用Erlang——一种为分布式计算应用优化的通用编程语言。

借助它，我们可以生成数百万个互相通信的小型erland进程。我们可以在分布式erlang应用中同时处理WebSocket连接和pub/sub频道。

不过，使用Erlang的一个挑战在于它是一种小众编程语言，很难招到实力强的erlang开发者。

## 第4步：总结

我们成功设计了一个支持附近的朋友功能的系统。

核心组件：
- **Web socket服务器**：客户端与服务器之间的实时通信
- **Redis**：位置数据的快速读写 + pub/sub频道

我们还探讨了如何扩展restful api服务器、websocket服务器、数据层、redis pub/sub服务器，也探讨了使用Redis Pub/Sub的替代方案。我们还探讨了“附近的随机陌生人”功能。
