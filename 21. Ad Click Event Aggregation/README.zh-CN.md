# 第 21 章：广告点击事件聚合

## 引言
**数字广告**是一个庞大的产业，随着 Facebook、YouTube、TikTok 等的崛起而发展壮大。

因此，跟踪广告点击事件非常重要。在本章中，我们探讨如何在 Facebook/Google 的规模下设计一个**广告点击事件聚合**系统。

数字广告有一个称为**实时竞价（RTB）**的过程，数字广告库存就在这个过程中被买卖：

<div style="margin-left:3rem">
    <img src="./images/digital-advertising-example.png" alt="digital-advertising-example" width="500" />
</div>

RTB 的速度很重要，因为它通常在一秒内完成。
数据准确性也非常重要，因为它影响广告主支付的金额。

基于广告点击事件聚合，广告主可以做出诸如调整目标受众和关键词之类的决策。

## 第 1 步：理解问题并确定设计范围
 - C：输入数据的格式是什么？
 - I：每天 10 亿次广告点击，总共有 200 万个广告。广告点击事件的数量同比增长 30%。
 - C：我们的系统需要支持的最重要的查询有哪些？
 - I：需要考虑的主要查询：
   - 返回广告 X 在最近 Y 分钟内的点击事件数
   - 返回过去 1 分钟内点击量最高的前 100 个广告。两个参数都应该是可配置的。聚合每分钟发生一次。
   - 支持对上述查询按 `ip`、`user_id`、`country` 进行数据过滤
 - C：我们需要考虑边界情况吗？我能想到一些：
   - 某些事件可能比预期更晚到达
   - 可能存在重复事件
   - 系统的不同部分可能宕机，因此我们需要考虑系统恢复
 - I：这份清单不错，把这些都考虑进去
 - C：延迟要求是什么？
 - I：广告点击聚合的端到端延迟为几分钟。对于 RTB，延迟则小于一秒。广告点击聚合可以容忍这样的延迟，因为它们通常用于计费和报表。

### **功能需求**
 - 聚合 `ad_id` 在最近 Y 分钟内的点击次数
 - 每分钟返回点击量最高的前 100 个 `ad_id`
 - 支持按不同属性进行聚合过滤
 - 数据量级达到 Facebook 或 Google 的规模

### **非功能需求**
 - 聚合结果的正确性很重要，因为它用于 RTB 和广告计费
 - 妥善处理延迟事件或重复事件
 - 健壮性——系统应能应对部分故障
 - 延迟——端到端延迟最多几分钟

### **粗略估算**
 - 10 亿 DAU
 - 假设每个用户每天点击 1 个广告 -> 每天 10 亿次广告点击
 - 广告点击 QPS = 10,000
 - 峰值 QPS 是该数字的 5 倍 = 50,000
 - 单次广告点击占用 0.1KB 存储。每日存储需求为 100gb
 - 每月存储 = 3tb

## 第 2 步：提出高层设计并获得认可
在本节中，我们讨论查询 API 设计、数据模型和高层设计。

### **查询 API 设计**
API 是客户端与服务端之间的契约。在我们的场景中，客户端是仪表盘用户——数据科学家/分析师、广告主等。

以下是我们的功能需求：
 - 聚合 `ad_id` 在最近 Y 分钟内的点击次数
 - 返回最近 M 分钟内点击量最高的前 N 个 `ad_id`
 - 支持按不同属性进行聚合过滤

我们需要两个端点来实现这些需求。过滤可以通过其中一个端点上的查询参数来完成。

**聚合 ad_id 在最近 M 分钟内的点击次数**：

```
GET /v1/ads/{:ad_id}/aggregated_count
```

查询参数：
 - from - 起始分钟。默认为 now - 1 min
 - to - 结束分钟。默认为 now
 - filter - 不同过滤策略的标识符。例如 001 表示“非美国点击”。

响应：
 - ad_id - 广告标识符
 - count - 起始分钟与结束分钟之间的聚合计数

**返回最近 M 分钟内点击量最高的前 N 个 ad_id**

```
GET /v1/ads/popular_ads
```

查询参数：
 - count - 点击量最高的前 N 个广告
 - window - 聚合窗口大小，单位为分钟
 - filter - 不同过滤策略的标识符

响应：
 - ad_id 列表

### **数据模型**
在我们的系统中，我们有原始数据和聚合数据。

原始数据看起来像这样：

```
[AdClickEvent] ad001, 2021-01-01 00:00:01, user 1, 207.148.22.22, USA
```

以下是结构化格式的示例：
| ad_id | click_timestamp     | user  | ip            | country |
|-------|---------------------|-------|---------------|---------|
| ad001 | 2021-01-01 00:00:01 | user1 | 207.148.22.22 | USA     |
| ad001 | 2021-01-01 00:00:02 | user1 | 207.148.22.22 | USA     |
| ad002 | 2021-01-01 00:00:02 | user2 | 209.153.56.11 | USA     |

以下是聚合后的版本：
| ad_id | click_minute | filter_id | count |
|-------|--------------|-----------|-------|
| ad001 | 202101010000 | 0012      | 2     |
| ad001 | 202101010000 | 0023      | 3     |
| ad001 | 202101010001 | 0012      | 1     |
| ad001 | 202101010001 | 0023      | 6     |

`filter_id` 帮助我们实现过滤需求。
| filter_id | region | IP        | user_id |
|-----------|--------|-----------|---------|
| 0012      | US     | *         | *       |
| 0013      | *      | 123.1.2.3 | *       |

为了支持快速返回最近 M 分钟内点击量最高的前 N 个广告，我们还会维护以下结构：
| most_clicked_ads   |           |                                                  |
|--------------------|-----------|--------------------------------------------------|
| window_size        | integer   | 聚合窗口大小（M），单位为分钟                    |
| update_time_minute | timestamp | 最后更新时间戳（以 1 分钟为粒度）                |
| most_clicked_ads   | array     | JSON 格式的广告 ID 列表。                        |

存储原始数据与存储聚合数据各有哪些优缺点？
 - 原始数据使我们能够使用完整的数据集，并支持数据过滤和重新计算
 - 另一方面，聚合数据使我们拥有更小的数据集和更快的查询
 - 原始数据意味着更大的数据存储和更慢的查询
 - 然而，聚合数据是派生数据，因此存在一定的数据丢失。

在我们的设计中，我们将结合使用这两种方法：
 - 保留原始数据用于调试是个好主意。如果聚合过程中存在 bug，我们可以发现 bug 并进行回填。
 - 聚合数据也应存储，以获得更快的查询性能。
 - 原始数据可以存储在冷存储中，以避免额外的存储成本。

在数据库方面，有几个因素需要考虑：
 - 数据长什么样？是关系型、文档型还是 blob？
 - 工作负载是读密集、写密集还是两者兼有？
 - 是否需要事务？
 - 查询是否依赖 SUM 和 COUNT 这类 OLAP 函数？

对于原始数据，我们可以看到平均 QPS 为 10k，峰值 QPS 为 50k，因此系统是写密集的。
另一方面，读流量很低，因为原始数据主要用作出现问题时的备份。

关系型数据库可以胜任，但扩展写入会很有挑战性。
或者，我们可以使用 Cassandra 或 InfluxDB，它们对高写入负载有更好的原生支持。

另一种选择是将 Amazon S3 与 ORC、Parquet 或 AVRO 这类列式数据格式结合使用。由于这种方案不太熟悉，我们仍然选择 Cassandra。

对于聚合数据，工作负载既是读密集也是写密集，因为聚合数据会不断被仪表盘和告警查询。
它也是写密集的，因为聚合服务每分钟都会聚合并写入数据。
因此，我们在这里也使用相同的数据存储（Cassandra）。

## 第 3 步：设计深入探讨
让我们深入探讨一些更有趣的话题。

### **流处理与批处理**
我们提出的高层架构是一种流处理系统。
以下是三种系统类型之间的对比：
|                         | 服务（在线系统）      | 批处理系统（离线系统）                          | 流处理系统（近实时系统）     |
|-------------------------|-------------------------------|--------------------------------------------------------|----------------------------------------------|
| 响应性          | 快速响应客户端 | 无需响应客户端                       | 无需响应客户端             |
| 输入                   | 用户请求                 | 有界输入，大小有限。大量数据 | 输入没有边界（无限流）     |
| 输出                  | 对客户端的响应          | 物化视图、聚合指标等           | 物化视图、聚合指标等 |
| 性能度量 | 可用性、延迟         | 吞吐量                                             | 吞吐量、延迟                          |
| 示例                 | 在线购物               | MapReduce                                              | Flink [13]                                   |

在我们的设计中，我们混合使用了批处理和流处理。

我们使用流处理来处理到达的数据，并近乎实时地生成聚合结果。
另一方面，我们使用批处理来进行历史数据备份。

一个同时包含批处理和流处理两条处理路径的系统，这种架构称为 lambda。
一个缺点是你要维护两条处理路径、两套不同的代码库。

Kappa 是一种替代架构，它将批处理和流处理合并到一条处理路径中。
其核心思想是使用单一的流处理引擎。

Lambda 架构：

Kappa 架构：

每当我们由于例如聚合逻辑中的重大 bug 而需要重新计算聚合数据时，我们都可以从存储的原始数据重新计算聚合。
 - 重新计算服务从原始存储中检索数据。这是一个批处理作业。
 - 检索到的数据被发送到专用的聚合服务，这样实时处理的聚合服务不会受到影响。
 - 聚合结果被发送到第二个消息队列，之后我们更新聚合数据库中的结果。

### **时间**
我们需要时间戳来执行聚合。它可以在两个地方生成：
 - 事件时间 - 广告点击发生的时间
 - 处理时间 - 服务器处理该事件时的系统时间

由于使用了异步处理（消息队列）和网络延迟，事件时间与处理时间之间可能存在显著差异。
 - 如果我们使用处理时间，聚合结果可能不准确
 - 如果我们使用事件时间，我们必须处理延迟事件

没有完美的解决方案，我们需要权衡取舍：
|                 | 优点                                  | 缺点                                                                                 |
|-----------------|---------------------------------------|--------------------------------------------------------------------------------------|
| 事件时间      | 聚合结果更准确 | 客户端的时间可能有误，或者时间戳可能由恶意用户生成 |
| 处理时间 | 服务器时间戳更可靠     | 如果事件延迟到达，时间戳就不准确                                       |

由于数据准确性很重要，我们将使用事件时间进行聚合。

为了缓解延迟事件的问题，可以使用一种称为“watermark”的技术。

### **投递保证**
由于我们聚合的数据将用于计费，数据准确性是首要的。

因此，我们需要讨论：
 - 如何避免处理重复事件
 - 如何确保所有事件都被处理

我们可以使用三种投递保证——最多一次、至少一次和恰好一次。

在大多数情况下，当少量重复可以接受时，至少一次就足够了。
然而我们的系统并非如此，因为很小的百分比差异就可能导致数百万美元的偏差。
因此，我们需要使用恰好一次投递语义。

### **数据去重**
最常见的数据质量问题之一是重复数据。

它可能来自多种来源：
 - 客户端 - 客户端可能多次重发同一个事件。带有恶意的重复事件最好由风控引擎处理。
 - 服务器故障 - 聚合服务节点在聚合过程中宕机，而上游服务尚未收到确认，因此事件被重发。

### **扩展系统**
让我们讨论系统增长时如何扩展。

我们有三个独立的组件——消息队列、聚合服务和数据库。
由于它们是解耦的，我们可以独立地扩展它们。

我们如何扩展消息队列：
 - 我们不对生产者设置限制，因此它们可以轻松扩展
 - 消费者可以通过分配到消费者组并增加消费者数量来扩展。
 - 为此，我们还需要确保预先创建了足够的分区
 - 此外，当消费者有数千个时，消费者再平衡可能需要一段时间，因此建议在非高峰时段进行
 - 我们也可以考虑按地理位置对主题进行分区，例如 `topic_na`、`topic_eu` 等。

### **容错**
在聚合节点内部，我们在内存中处理数据。如果某个节点宕机，已处理的数据就会丢失。

### **数据监控与正确性**
由于我们聚合的数据至关重要，因为它用于计费，因此必须建立严格的监控以确保正确性。

我们可能希望监控的一些指标：
 - **延迟**：可以跟踪不同事件的时间戳，以了解系统的端到端延迟
 - **消息队列大小**：如果队列大小突然增加，我们需要增加聚合节点。由于 Kafka 是通过分布式提交日志实现的，我们需要跟踪的是 records-lag 指标。
 - **聚合节点上的系统资源**：CPU、磁盘、JVM 等。
