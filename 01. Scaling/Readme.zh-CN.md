# 第 1 章：从零扩展到数百万用户

## 引言
将系统扩展到支持数百万用户是一个复杂且迭代的过程，需要不断改进与优化。本章概述如何从单台服务器部署起步，逐步扩展架构以应对数百万用户。

---

## 第 1 节：单服务器部署
最初，所有组件（Web 应用、数据库、缓存）都运行在一台服务器上。

<div style="margin-left:3rem">
   <img src="./images/single-server.png" width="400" />
</div>

### 请求流程
1. 用户通过域名（例如 `api.mysite.com`）访问应用，域名由 DNS 解析为 IP 地址。
2. Web 服务器的 IP 地址被返回给浏览器或移动应用。
3. HTTP 请求被发送到 Web 服务器，服务器返回 HTML 或 JSON 响应。

### 流量来源
1. **Web 应用：** 使用服务端语言（例如 Python、Java）处理业务逻辑，使用客户端语言（例如 JavaScript、HTML）负责呈现。
2. **移动应用：** 使用 HTTP 和 JSON 与 Web 服务器通信，进行轻量级数据交换。

---

## 第 2 节：数据库分离
随着用户规模增长，数据库被迁移到专用服务器，以便 Web 层与数据库层可以独立扩展。

<div style="margin-left:3rem">
   <img src="./images/database.png" width="400" />
</div>

### 数据库选型

1. **关系型数据库（SQL）：** 结构化数据存储在表中。示例：MySQL、PostgreSQL。
2. **非关系型数据库（NoSQL）：** 适用于非结构化数据或低延迟需求。类别包括：
   - 键值存储
   - 图数据库
   - 列式存储
   - 文档存储

- 在以下情况下，非关系型数据库可能是合适的选择：
   - 应用需要极低延迟。
   - 数据是非结构化的，或者不存在关系型数据。
   - 只需要对数据（JSON、XML、YAML 等）进行序列化和反序列化。
   - 需要存储海量数据。

---

## 第 3 节：垂直扩展与水平扩展
### 垂直扩展
- 为现有服务器增加更多资源（CPU、RAM）。
- 受硬件限制约束，且缺乏冗余。

### 水平扩展
- 向服务器池中加入更多服务器，更适合大规模系统。
- 使用负载均衡器处理服务器之间的请求路由。
---

## 第 4 节：负载均衡器

<div style="margin-left:3rem">
   <img src="./images/load-balancer.png" width="400" />
</div>

**负载均衡器**将流量分发到多台服务器。其优势包括：
1. 冗余：如果某台服务器下线，流量会被重新路由。
   -  如果服务器 1 下线，所有流量都会被路由到服务器 2。
2. 可扩展性：可轻松添加服务器以应对流量高峰。
   -  如果网站流量快速增长，可以继续添加服务器来处理额外的流量。

---

## 第 5 节：数据库复制

<div style="margin-left:3rem">
   <img src="./images/database-replication.png" width="400" />
</div>

### 主从模型
- **主数据库：** 处理写操作。
   - 所有修改数据的命令，如插入、删除或更新，都必须发送到主数据库。
- **从数据库：** 处理读操作，提升性能与可靠性。
   - 由于大多数应用的读写比较高，因此系统中从数据库的数量通常多于主数据库的数量。

### 优势
1. 通过并行的读操作提升性能。
2. 通过冗余实现高可用与数据可靠性。


### 故障处理
- 如果只有一台从数据库可用且它下线了，读操作会被临时定向到主数据库。
- 如果存在多台可用的从数据库，读操作会被重定向到其他健康的从数据库，并由新服务器替换旧服务器。
- 如果主数据库下线，某台从数据库会被提升为新的主数据库。
- 在生产系统中，被选中的从数据库可能不是最新的，因此需要通过运行数据恢复脚本来更新数据（多主、环形复制等方法可能有所帮助）。

## 第 6 节：缓存
**缓存**将频繁访问的数据存储在内存中，以减轻数据库负载。缓存层是一个临时数据存储层，速度远快于数据库。

<div style="margin-left:3rem">
   <img src="./images/cache.png" width="500" />
</div>

### 缓存注意事项
1. **使用场景**：当数据被频繁读取但很少修改时，考虑使用缓存。
2. **过期策略：** 缓存数据一旦过期，就会从缓存中被移除。如果没有过期策略，缓存数据将永久存储在内存中。
3. **一致性：** 这意味着保持数据存储与缓存同步。由于对数据存储与缓存的修改操作不在同一个事务中，因此可能出现不一致。
4. **缓解故障**：单台缓存服务器意味着潜在的单点故障，建议在不同数据中心部署多台缓存服务器以避免 SPOF。
5. **淘汰策略：** 缓存满后，需要淘汰条目以释放内存。LRU 是最流行的缓存淘汰策略。

---

## 第 7 节：内容分发网络（CDN）
**CDN**通过在地理上分布的服务器上缓存静态内容（图片、CSS、JavaScript）来缩短加载时间。

<div style="margin-left:3rem">
   <img src="./images/cdn.png" width="400" />
</div>

### 工作流程
1. 用户向最近的 CDN 服务器请求内容。
2. 如果未命中，则从源服务器获取内容并缓存。


### CDN 注意事项
1. **成本：** CDN 由第三方提供商运营，会对进出 CDN 的数据传输收费。
2. **缓存过期：** 缓存过期时间既不应过长，也不应过短。
3. **CDN 回退：** 如果 CDN 出现临时故障，客户端应能检测到该问题并从源服务器请求资源。
4. **文件失效：** 如果文件被更新，应使缓存失效，以指向更新后的文件。

## 第 8 节：无状态 Web 层
通过将会话数据移到共享数据存储中，Web 服务器变得无状态。这样可以：
1. 更轻松地水平扩展。
2. 基于流量自动伸缩。

## 第 9 节：多数据中心部署
跨多个数据中心部署可提升可用性并降低延迟。策略包括：

<div style="margin-left:3rem">
   <img src="./images/data-center.png" width="400" />
</div>

1. **GeoDNS 路由：** 将用户引导至最近的数据中心。
2. **数据复制：** 在多个数据中心之间同步数据以防止不一致。

### 关键考量
- **流量重定向：** 需要有效的工具将流量引导到正确的数据中心。
- **数据同步：** 一种常见策略是在多个数据中心之间复制数据。
- **测试与部署：** 自动化部署工具对于保持所有数据中心的服务一致性至关重要。

---

## 第 10 节：消息队列
**消息队列**是一个持久化组件，存储在内存中，支持异步通信。它充当缓冲区，分发异步请求。

<div style="margin-left:3rem">
   <img src="./images//message-queue.png" width="500" />
</div>

- 输入服务称为生产者/发布者，它们创建消息并将其发布到消息队列。
- 其他服务称为消费者/订阅者，它们连接到队列，并执行消息所定义的操作。

## 第 12 节：数据库扩展
### 垂直扩展
- 增加硬件资源，但存在物理与成本限制。
- 有多个缺点：
   -  单点故障风险更大。
   -  垂直扩展的总体成本很高

### 水平扩展（分片）

<div style="margin-left:3rem">
   <img src="./images/horizontal-scaling.png" width="400" />
</div>

- 使用键（例如 `user_id`）将数据划分到多个分片。
   - 分片将大型数据库拆分为更小、更易管理的部分，称为分片。
   - 每个分片共享相同的模式，但每个分片上的实际数据是该分片独有的。
- 在实现分片策略时，分片键至关重要。选择分片键时，重要的是选择能够均匀分布数据的键。

#### 挑战
1. **重新分片数据：** 在以下情况下需要重新分片数据：
   - 由于快速增长，单个分片无法再容纳更多数据。
   - 由于数据分布不均，某些分片可能比其他分片更快耗尽。
   - 使用一致性哈希来克服这些问题

2. **名人问题：** 对某个特定分片的过度访问可能导致服务器过载。
   - 为解决这个问题，我们可能需要为每个名人分配一个分片。

3. **连接与反规范化：** 一旦数据库被分片到多台服务器上，跨数据库分片执行连接操作就很困难。
   - 一种常见的变通方法是对数据库进行反规范化，使查询可以在单张表中执行。

---

## 结论
### 关键要点
1. 保持 Web 层无状态。
2. 在每一层构建冗余。
3. 使用缓存和 CDN 优化性能。
4. 通过分片扩展数据层。
5. 解耦组件以获得灵活性。

本章为构建能够支撑数百万用户的可扩展系统奠定了坚实基础。
