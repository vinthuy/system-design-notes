# 第 23 章：分布式电子邮件服务

## 引言

本章我们将设计一个**分布式电子邮件服务**，与**Gmail**类似。

2020 年，**Gmail** 有 18 亿活跃用户，而**Outlook** 在全球有 4 亿用户。

---

## 第 1 步：理解问题并确立设计范围

- C：系统有多少用户使用？
- I：10 亿用户
- C：我认为以下功能很重要——认证、发送/接收邮件、获取邮件、过滤邮件、搜索邮件、反垃圾邮件保护。
- I：清单不错。暂时不用考虑认证。
- C：用户如何与邮件服务器连接？
- I：通常，电子邮件客户端通过 SMTP、POP、IMAP 连接，但这个问题中我们使用 HTTP。
- C：邮件可以带附件吗？
- I：可以

### **非功能性需求**

- **可靠性**——我们不应该丢失数据
- **可用性**——我们应该使用复制来防止单点故障。我们还应该容忍部分系统故障。
- **可扩展性**——随着用户群增长，我们的系统应该能够处理他们。
- **灵活性和扩展性**——系统应该灵活，并且易于通过新功能进行扩展。这也是我们选择 HTTP 而非 SMTP/其他邮件协议的原因之一。

### **粗略估算**

- **10 亿用户**
- 假设每人每天发送 10 封邮件 -> **每秒 10 万封邮件**。
- 假设每人每天接收 40 封邮件，且每封邮件平均有 50kb 元数据 -> **每年 730pb 存储**。
- 假设 20% 的邮件带有存储附件，平均大小为 500kb -> **每年 1,460pb**。

## 第 2 步：提出高层设计并获得认可

### **电子邮件基础知识 101**

用于发送和接收电子邮件的协议有多种：
- **SMTP**——从一台服务器向另一台服务器发送电子邮件的标准协议。
- **POP**——从远程邮件服务器接收并下载电子邮件到本地客户端的标准协议。邮件一旦被取回，就会从远程服务器上删除。
- **IMAP**——与 POP 类似，用于从远程服务器接收和下载电子邮件，但它会把邮件保留在服务器端。
- **HTTPS**——严格来说不是电子邮件协议，但可用于基于 Web 的电子邮件客户端。

除了邮件协议之外，我们还需要为电子邮件服务器配置一些 DNS 记录——MX 记录：

电子邮件附件以 base64 编码发送，且大多数邮件服务通常有 25mb 的大小限制。
该限制是可配置的，并且个人账户与企业账户有所不同。

### **传统邮件服务器**

当用户数量有限且连接到单台服务器时，传统邮件服务器可以很好地工作。

<div style="margin-left:3rem">
    <img src="./images/traditional-mail-server.png" alt="传统邮件服务器" width="500" />
</div>

- Alice 登录她的 Outlook 邮箱并按下“发送”。邮件被发送到 Outlook 邮件服务器。通信通过 SMTP 进行。
- Outlook 服务器查询 DNS 以找到 gmail.com 的 MX 记录，并将邮件传输到他们的服务器。通信通过 SMTP 进行。
- Bob 通过 IMAP/POP 从他的 gmail 服务器获取邮件。

在传统邮件服务器中，邮件存储在本地文件系统上。每封邮件都是一个单独的文件。

<div style="margin-left:3rem">
    <img src="./images/local-dir-storage.png" alt="本地目录存储" width="500" />
</div>

随着规模增长，磁盘 I/O 成为瓶颈。此外，它也无法满足我们的高可用性和可靠性要求。
磁盘可能损坏，服务器也可能宕机。

### **分布式邮件服务器**

分布式邮件服务器旨在支持现代用例，并解决现代可扩展性问题。

这些服务器仍然可以为原生电子邮件客户端支持 IMAP/POP，并支持跨服务器邮件交换的 SMTP。

但对于功能丰富的基于 Web 的邮件客户端，通常使用基于 HTTP 的 RESTful API。

示例 API：
- `POST /v1/messages`——向 To、Cc、Bcc 头中的收件人发送消息。
- `GET /v1/folders`——返回电子邮件账户的所有文件夹

示例响应：

```
[{id: string        Unique folder identifier.
  name: string      Name of the folder.
                    According to RFC6154 [9], the default folders can be one of
                    the following: All, Archive, Drafts, Flagged, Junk, Sent,
                    and Trash.
  user_id: string   Reference to the account owner
}]
```

- `GET /v1/folders/{:folder_id}/messages`——带分页返回某个文件夹下的所有消息
- `GET /v1/messages/{:message_id}`——获取某条特定消息的所有信息

示例响应：

```
{
  user_id: string                      // Reference to the account owner.
  from: {name: string, email: string}  // <name, email> pair of the sender.
  to: [{name: string, email: string}]  // A list of <name, email> paris
  subject: string                      // Subject of an email
  body: string                         //  Message body
  is_read: boolean                     //  Indicate if a message is read or not.
}
```

<div style="margin-left:3rem">

- **网页邮箱**——用户使用 Web 浏览器发送/接收电子邮件
- **Web 服务器**——面向公众的请求/响应服务，用于管理登录、注册、用户资料等。
- **实时服务器**——用于将新邮件更新实时推送给客户端。我们使用 websocket 进行实时通信，但对于不支持 websocket 的旧浏览器会回退到长轮询。
- **元数据数据库**——存储邮件元数据，如主题、正文、发件人、收件人等。
- **附件存储**——对象存储（例如 Amazon S3），适合存储大文件。
- **分布式缓存**——我们可以在 Redis 中缓存最近的邮件以改善用户体验。
- **搜索存储**——分布式文档存储，用于支持全文搜索。

以下是邮件发送流程的样子：

<div style="margin-left:3rem">
    <img src="./images/email-sending-flow.png" alt="邮件发送流程" width="500" />
</div>

- 用户撰写邮件并按下“发送”。邮件被发送到负载均衡器。
- 负载均衡器对过量的邮件发送进行限流，并路由到其中一台 Web 服务器。
- Web 服务器进行基本的邮件校验（例如邮件大小），如果域名与发件人相同则短路出站流程。但会先做垃圾邮件检查。
- 如果基本校验通过，邮件被发送到消息队列（附件从对象存储中引用）
- 如果基本校验失败，邮件被发送到错误队列
- SMTP 出站工作进程从出站队列拉取消息，进行垃圾邮件/病毒检查，并路由到目标邮件服务器。
- 邮件被存储在“已发送邮件”文件夹中

我们还需要监控出站消息队列的大小。增长过大可能表明存在问题：
- 收件人的邮件服务器不可用。我们可以使用指数退避稍后重试发送邮件。
- 消费者不足以处理负载，我们可能需要扩展消费者。

以下是邮件接收流程：

<div style="margin-left:3rem">
    <img src="./images/email-receiving-flkow.png" alt="邮件接收流程" width="500" />
</div>

- 入站邮件到达 SMTP 负载均衡器。邮件被分发到 SMTP 服务器，在那里执行邮件接收策略（例如无效邮件会被直接丢弃）。
- 如果邮件的附件太大，我们可以将其放入对象存储（s3）。
- 邮件处理工作进程进行初步检查，之后邮件被转发到存储、缓存、对象存储和实时服务器。
- 离线用户重新上线后，会通过 HTTP API 获取他们的新邮件。

### **元数据数据库**

以下是电子邮件元数据的一些特征：
- 头部通常很小，且访问频繁
- 正文大小从很小到很大不等，但通常只读取一次
- 大多数邮件操作都局限于单个用户——例如获取邮件、标记为已读、搜索。
- 数据的新近程度会影响数据的使用。用户通常只阅读最近的邮件
- 数据有很高的可靠性要求。数据丢失是不可接受的。

在 gmail/outlook 的规模下，数据库通常是定制的，以减少每秒输入/输出操作数（IOPS）。

让我们考虑一下有哪些数据库选项：
- **关系型数据库**——我们可以为头部和正文建立索引，但这些数据库通常针对小块数据进行了优化。
- **分布式对象存储**——这可能是备份存储的好选择，但无法高效支持搜索/标记为已读等操作。
- **NoSQL**——Google BigTable 被 gmail 使用，但它并未开源。

基于以上分析，很少有现有解决方案能完美契合我们的需求。
在面试环境中，设计一个新的分布式数据库方案是不可行的，但说明其特征很重要：
- 单列可以达到个位数 MB
- 强数据一致性
- 旨在减少磁盘 I/O
- 高可用且容错
- 应该易于创建增量备份

为了对数据分区，我们可以使用 `user_id` 作为分区键，这样单个用户的数据会存储在单个分片上。
这使得我们无法与多个用户共享一封邮件，但这不是本次面试的要求。

让我们定义表：
- 主键由分区键（数据分布）和聚类键（数据排序）组成
- 我们需要支持的查询——获取某个用户的所有文件夹、显示某个文件夹中的所有邮件、创建/获取/删除邮件、获取已读/未读邮件、获取会话线程（加分项）

### **邮件送达率**

搭建一台服务器来发送邮件很容易，但由于垃圾邮件防护算法，让邮件进入收件人的收件箱却很难。

如果我们只是搭建一个新的邮件服务器并开始通过它发送邮件，我们的邮件很可能最终进入垃圾邮件文件夹。

以下是我们为防止这种情况可以做的事情：
- **专用 IP**——使用专用 IP 发送邮件，否则收件服务器不会信任你。
- **对邮件分类**——避免从相同的服务器发送营销邮件，以防更重要的邮件被归类为垃圾邮件
- **缓慢预热你的 IP 地址**，以与大型电子邮件提供商建立良好声誉。预热一个新的 IP 需要 2 到 6 周
- **快速封禁垃圾邮件发送者**，以免损害你的声誉
- **反馈处理**——与 ISP 建立反馈回路，以跟踪投诉率并快速封禁垃圾邮件账户。
- **邮件认证**——使用常见技术来对抗钓鱼，例如 Sender Policy Framework、DomainKeys Identified Mail 等。

你不需要记住所有这些。只需要知道，构建一个好的邮件服务器需要大量的领域知识。

### **搜索**

搜索包括基于邮件内容进行全文搜索，或基于发件人、收件人、主题、未读等过滤器进行更高级的查询。

邮件搜索的一个特点是它局限于用户本地，且写入多于读取，因为我们需要在每次操作时重新索引，但用户很少使用搜索标签页。

让我们比较 Google 搜索与邮件搜索：

|               | 范围                | 排序                               | 准确性                                          |
|---------------|----------------------|---------------------------------------|---------------------------------------------------|
| Google 搜索 | 整个互联网   | 按相关性排序                     | 索引需要一些时间，因此结果不是即时的。 |
| 邮件搜索  | 用户自己的邮箱 | 按属性排序，例如时间、日期等 | 索引应该快速，结果应该准确。    |

为了支持这种搜索功能，一种选择是使用 Elasticsearch 集群。我们可以使用 `user_id` 作为分区键，将数据分组到同一节点下：

变更操作通过 Kafka 异步进行，以便将服务与重新索引流程解耦。
而实际的数据搜索是同步进行的。

Elasticsearch 是最流行的搜索引擎数据库之一，对邮件的全文搜索支持得非常好。

或者，我们可以尝试开发自己的定制搜索方案，以满足我们的特定需求。

设计这样一个系统超出了本文的范围。构建它时的核心挑战之一，是为写密集的工作负载进行优化。

为此，我们可以使用日志结构合并树（LSM）在磁盘上组织索引数据。写入路径仅针对顺序写入进行优化。
该技术用于 Cassandra、BigTable 和 RocksDB。

其核心思想是将数据保存在内存中，直到达到预定义的阈值，之后将其合并到下一层（磁盘）：

<div style="margin-left:3rem">

</div>

两种方法之间的主要权衡：
- Elasticsearch 可以扩展到一定程度，而定制搜索引擎可以针对邮件用例进行微调，从而进一步扩展。
- Elasticsearch 是我们需要与元数据存储一起维护的独立服务。定制方案可以就是数据存储本身。
- Elasticsearch 是现成的解决方案，而定制搜索引擎需要大量的工程投入来构建。

## 第 4 步：总结

额外的讨论点：
- **容错**——系统的许多部分都可能发生故障。我们如何处理节点故障值得讨论。
- **合规**——鉴于欧洲的 GDPR 法律，PII 需要以合理的方式存储。
- **安全**——邮件加密、钓鱼防护、安全浏览等。
- **优化**——例如防止同一附件被不同用户多次发送造成的重复。
