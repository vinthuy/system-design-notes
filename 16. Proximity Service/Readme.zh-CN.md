# 第 16 章：邻近服务

## 简介
**邻近服务**旨在查找附近的地点，例如餐厅、酒店、加油站以及其他商户。**Google Maps** 和 **Yelp** 等应用都使用了这一功能，帮助用户发现在指定半径内的地点。


## 第 1 步：理解问题并确定范围

### **功能需求**
1. **根据用户位置（纬度、经度）和搜索半径搜索商户**。
2. **允许商户所有者**添加、更新或删除商户（非实时）。
3. **在被请求时提供商户的详细信息**。

### **非功能需求**
- **低延迟**：用户应当快速获得响应。
- **数据隐私**：符合 GDPR 和 CCPA 法规。
- **高可用**：应对繁忙地点的高峰时段流量尖峰。

### **粗略估算**
- **1 亿日活跃用户**。
- 系统中**2 亿商户**。
- **搜索 QPS 计算**：
  - 用户**每天搜索 5 次**。
  - **搜索 QPS** = (100M × 5) / 86,400 ≈ **5,000 QPS**。

## 第 2 步：高层设计

### **API 设计**
#### **搜索附近商户**
GET /v1/search/nearby

- **请求参数**：
  - `latitude`：用户所在位置的纬度。
  - `longitude`：用户所在位置的经度。
  - `radius`：搜索半径（默认：5000m）。

#### **商户 API**
| API 端点                     | 描述                                      |
|-----------------------------------|--------------------------------------------------|
| `GET /v1/businesses/{id}`         | 获取商户详细信息                    |
| `POST /v1/businesses`             | 新增商户                              |
| `PUT /v1/businesses/{id}`         | 更新商户详情                         |
| `DELETE /v1/businesses/{id}`      | 从系统中移除商户               |


### **数据模型**
- 由于这两个功能都非常常用，读取量很大，因此像 MySQL 这样的关系型数据库是合适的选择。
  - 搜索附近的商户
  - 查看某个商户的详细信息

### **数据模式**
- 关键的数据库表是商户表和地理空间索引表
- 商户表包含某个商户的详细信息。

### **高层系统架构**
系统由两部分组成：基于位置的服务（LBS）和商户相关服务。

<div style="margin-left:3rem">
    <img src="./images/high-level-design.png" alt="HLD" width="400" />
</div>

- **基于位置的服务（LBS）**：
  - 处理基于位置的搜索查询。
  - 读多写少的服务，没有写请求。
  - QPS 很高，尤其是在人口密集区域的高峰时段，并且系统是无状态的。
- **商户服务**：处理两类请求。
  - 商户所有者创建、更新或删除商户。
  - 客户查看某个商户的详细信息。
- **负载均衡器**：将流量路由到 LBS 和商户服务。
- **数据库集群**：
  - 针对读多写少的负载采用**主从（primary-replica）架构**。
  - LBS 读取的数据与主数据库写入的数据之间可能存在一些差异。
  - 这种不一致不是问题，因为商户信息不是实时更新的。

## 第 3 步：获取附近商户的算法

### **方案 1：二维搜索（朴素方法）**

<div style="margin-left:3rem">
    <img src="./images/2d-search.png" alt="2D" width="250" />
</div>

最直观的做法是以预先定义的半径画一个圆，并找出圆内的所有商户。

**SQL 查询：**
```
SELECT business_id, latitude, longitude
FROM business
WHERE (latitude BETWEEN :lat - radius AND :lat + radius)
AND (longitude BETWEEN :long - radius AND :long + radius);
```
**问题：**
- **效率低下**：需要扫描整个数据库。
- **受一维索引的限制**（纬度/经度）。

一种潜在的改进是在经度和纬度列上建立索引，虽然这稍好一些，但仍然非常慢。

### 更好的方法
- 上一种方法的问题在于，数据库索引只能在一个维度上提升搜索速度。
- 更优的做法是利用地理空间索引将二维数据表示为一维数据。
  - 哈希：均匀网格、Geo Hash
  - 树：四叉树、Google S2、RTree

  <div style="margin-left:3rem">
    <img src="./images/geospatial-index-types.png" alt="2D" width="500" />
  </div>


### **方案 2：均匀划分的网格**

  <div style="margin-left:3rem">
    <img src="./images/even-grid.png" alt="均匀网格" width="400" />
  </div>

- **将世界划分为固定大小的网格**。
- **问题**：商户分布不均匀（城市中密度高，乡村地区稀疏）。

### **方案 3：Geohash**
- 沿本初子午线和赤道将地球划分为四个象限。然后将每个网格划分为四个更小的网格。
- 每个网格可以通过交替经度和纬度比特来表示。
- 重复这种细分

  <div style="margin-left:3rem">
    <img src="./images/geohash.png" alt="Geohash" width="300" />
    <img src="./images/geohash-1.png" alt="Geohash" width="285" />
  </div>


- **将纬度和经度编码为一个字母数字字符串**。它有 12 个精度（层级）
- **层次化的网格结构**使得高效搜索成为可能。
- 根据表格选择最小的 geohash 长度，从而确定合适的精度。
  <div style="margin-left:3rem">
    <img src="./images/geohash-radius-mapping.png" alt="Geohash 半径" width="400" />
  </div>
- Geohash 保证两个 geohash 之间的共享前缀越长，它们就越接近。

- **挑战**：
  <div style="margin-left:3rem">
    <img src="./images/boundary-issue.png" alt="边界问题" width="300" />
  </div>

  - **边界问题**（靠近网格边界的商户可能被排除在外）。
    - 两个位置可能非常接近，但完全没有共享前缀（可能位于赤道的另一侧）
    - 两个位置可能共享很长的前缀，但属于不同的 geohash。
  - 解决方案：需要搜索相邻的网格。


### **方案 4：四叉树**

  四叉树是一种树形数据结构，它递归地将二维空间划分为四个象限，每个内部节点正好有四个子节点，分别代表该空间的四个子区域。
  - 四叉树是内存数据结构，运行在每个 LBS 服务器上，并在服务器启动时构建。

  <div style="margin-left:3rem">
    <img src="./images/quadtree.png" alt="四叉树" width="500" />
  </div>

  - 根节点被递归地拆分为 4 个象限，直到没有节点还包含超过 x 个商户（本例中为 100 个）。

  <div style="margin-left:3rem">
    <img src="./images/building-quadtree.png" alt="构建四叉树" width="500" />
  </div>

- 四叉树索引占用的内存并不多（通常是 GB 级别），可以轻松地放在一台服务器上。
- 由于构建树的时间复杂度是 nlogn，构建这棵树可能需要几分钟。
- **对 k 最近邻搜索查询高效**（例如，找到最近的加油站）。

  <div style="margin-left:3rem">
    <img src="./images/realworld-quadtree.png" alt="真实世界四叉树" width="400" />
  </div>

#### 运维方面的考量
 - 对于约 2 亿商户，在服务器启动时构建一棵四叉树可能需要几分钟。
 - 在四叉树构建期间它无法对外提供服务，因此新版本应逐步发布到一部分服务器上。
 - 更新商户或新增商户时，最简单的做法是增量重建四叉树。（会导致大量缓存失效）
 - 也可以动态更新四叉树，但实现起来更复杂。（需要加锁机制）

### **方案 5：Google S2**
它基于 Hilbert 曲线将球体映射到 !D 索引。在 Hilbert 曲线上彼此接近的两个点在 1D 空间中也接近。


  <div style="margin-left:3rem">
    <img src="./images/hilbert-curve.png" alt="Hilbert 曲线" width="300" />
    <img src="./images/geofence.png" alt="地理围栏" width="355" />
  </div>

- **使用 Hilbert 曲线将地球划分为小的单元格**。
- 非常适合地理围栏，因为它能以不同层级覆盖任意区域。
- 地理围栏还允许定义围绕感兴趣区域的参数。
- 另一个优势是，我们不必使用固定的精度层级，而是可以在 S2 中指定最小层级、最大层级和最大单元格数。


## 权衡比较

#### Geohash
- 易于使用和实现——无需构建/重建树
- 支持固定半径的结果
- 更新索引很容易。
- 无法根据人口密度动态调整网格大小。

#### 四叉树
- 实现起来稍难一些。
- 支持获取 k 个最近的商户。
- 可以根据人口密度动态调整网格大小。
- 更新索引更复杂，因为可能需要重建整棵树。

## 第 4 步：数据库扩展与缓存策略

### **商户表的扩展**
- **按商户 ID 分片**可确保数据均匀分布。
- 表中每个商户都有单独的行。

| Geohash | 商户 ID |
|---------|------------|
| 9q9hvu  | 343        |
| 9q9hvu  | 347        |
| 9q9hvu  | 112        |

### **地理空间索引的扩展**
- geohash 表可能不太适合分片。在这种情况下，所有数据都能放进一台服务器，因此没有分片的技术理由。
- 更好的做法是使用只读副本（read replica）来分担读负载。



---

### **缓存策略**
最显而易见的缓存键选择是位置坐标，但它存在几个问题：
 - 来自 GPS 的位置坐标并不准确。
 - 用户可能移动，导致位置坐标发生变化。
 - 更好的键是 geohash。

| 缓存键  | 缓存值 |
|------------|------------|
| `geohash`  | 该网格中商户 ID 的列表 |
| `business_id` | 商户详情（名称、地址、评论等） |

## 获取附近商户的步骤
1. **用户请求：**  
   - 用户搜索 **500 米**范围内的餐厅。  
   - 客户端将**纬度（37.776720）、经度（-122.416730）和半径（500m）**发送给**负载均衡器**。

2. **请求转发：**  
   - **负载均衡器（LB）**将请求转发给**基于位置的服务（LBS）**。

3. **Geohash 计算：**  
   - LBS 确定与半径相匹配的 **geohash 长度**。  
   - 通过参考表可知，**500m 对应 geohash 长度 = 6**。

4. **获取相邻的 geohash：**  
   - LBS 计算**相邻的 geohash**，以包含附近的区域。  
   - 结果是一个列表：  
     ```
     [my_geohash, neighbor1_geohash, neighbor2_geohash, ..., neighbor8_geohash]
     ```

5. **从 Redis 获取商户 ID：**  
   - 对于列表中的每个 geohash，LBS 查询 **Geohash Redis 服务器**以获取**商户 ID**。  
   - 使用并行查询以最小化延迟。

6. **检索并对商户排序：**  
   - LBS 从**商户信息 Redis 服务器**获取**完整的商户详情**。  
   - 商户按与用户位置的距离**排序**。  
   - **排序后的结果**被返回给客户端。

## 关键优化
- **并行 Redis 调用**：缩短响应时间。  
- **Geohash 索引**：确保高效的空间查询。  
- **缓存**：加速商户数据的查找与获取。  

这种方法确保了能以**低延迟、可扩展**的方式检索用户附近的商户。

---

### **选择最佳索引方法**
| 索引方法 | 优点 | 缺点 |
|----------------|------|------|
| **Geohash** | 易于实现，对邻近搜索高效 | 边界问题，网格大小固定 |
| **四叉树** | 根据密度动态调整，支持 k 最近邻查询 | 更复杂，需要树再平衡 |
| **Google S2** | 高级地理围栏能力，用于 Google Maps | 实现难度更高 |
