# 第 2 章：粗略估算

## 引言
粗略估算（back-of-the-envelope estimation）是系统设计面试中一项至关重要的技能。它指的是通过快速、粗略的计算来评估系统容量或性能。Google 高级研究员 Jeff Dean 认为，这些估算借助思想实验和常见的性能基准，帮助判断设计是否满足需求。

本章介绍关键概念、方法论和示例，以帮助读者熟练掌握可扩展性与估算。

### 每个程序员都应该知道的延迟数值
延迟数值表示计算系统中各种操作所耗费的时间。它们提供了关于相对性能的洞见：

| 操作                     | 延迟（2020 年） |
|--------------------------|----------------|
| L1 缓存访问              | 0.5 ns         |
| L2 缓存访问              | 7 ns           |
| 主存访问                 | 100 ns         |
| SSD 随机读               | 150 µs         |
| HDD 随机寻道             | 10 ms          |
| 数据中心内往返           | 500 µs         |
| 跨区域数据中心           | 150 ms         |

**关键洞见：**
- 内存快，磁盘慢。
- 尽可能避免磁盘寻道。
- 在通过互联网传输数据之前先压缩数据，以节省带宽。


---

### 可用性数值
高可用（HA）确保停机时间最小化。可用性以**几个 9**来表示：
- **99%（两个 9）：**每年约 3.65 天停机时间
- **99.9%（三个 9）：**每年约 8.8 小时停机时间
- **99.99%（四个 9）：**每年约 52 分钟停机时间
- **99.999%（五个 9）：**每年约 5.3 分钟停机时间
- **99.9999%（六个 9）：**每年约 31.56 秒停机时间


Amazon、Google 和 Microsoft 等云服务商的目标是达到 **99.9% 或更高**的 SLA（服务等级协议）。

## 第 2 节：估算示例——Twitter 的 QPS 与存储需求

### 假设
- **月活跃用户（MAU）3 亿。**
- **日活跃用户（DAU）占 50%。**
- **平均每用户每日发推数：**2 条。
- **10% 的推文包含媒体。**
- **数据保留期：**5 年。

### 估算
1. **每秒查询数（QPS）：**
   - DAU = \( 300M x 50\% = 150M \)
   - 推文 QPS = \( 150M x 2 tweets / 24 hour / 3600 seconds = ~3500 )
   - 峰值 QPS = \( 2 x 3500 = ~7000 \)

2. **媒体存储：**
   - **推文大小组成：**
     - `tweet_id`：64 字节
     - `text`：140 字节
     - `media`：1 MB
   - **每日媒体存储：**\( 150M x 2 x 10\% x 1MB = 30TB per day \)
   - **5 年存储量：**\( 30TB x 365 x 5 = ~55PB \)

## 第 3 节：有效估算的技巧

### 1. 取整与近似
精度并不关键，重点在于过程。用整数简化复杂计算。例如：
- \( 99987 / 9.1 \) 可以近似为 \( 100,000 / 10 = 10,000 \)。

### 2. 写下假设
清楚地记录假设，以便日后参考。

### 3. 标注单位
通过标注单位来避免歧义（例如用 `5 MB` 而不是 `5`）。

### 4. 常见估算场景
- **QPS（每秒查询数）：**衡量流量强度。
- **峰值 QPS：**考虑流量尖峰。
- **存储需求：**估算数据总量需求。
- **缓存需求：**评估缓存所需的内存。
- **服务器数量：**根据工作负载计算硬件需求。
